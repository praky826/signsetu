# Phase 9 Completion Summary — WebSocket Bridge, App Assembly & Static Serving (Step 9, Step 15, main.py)

Files completed: backend/main.py (mounts frontend/ as static files with html=True at root; mounts frontend/vendor/models/ at /models for avatar.js's hardcoded GLB path; registers the WebSocket route at /ws; starts three background tasks - chunker.run_loop(), whisper_service.run_loop(), connection.run_render_loop() - and cancels them on shutdown); backend/ws/connection.py (complete - receive half extended to distinguish binary audio from JSON text control messages via websocket.receive(), plus the new run_render_loop()).

Cross-boundary additions: two JSON control message types, frontend to backend, neither given an exact shape in the docs and decided here: {"type": "set_mode", "mode": "video"|"avatar"} and {"type": "seek", "sessionId": "<id>"}. Backend to frontend: one render instruction per text message, the frozen {word, renderType, assetRef, sessionId} shape, sent only when session_state.is_current() confirms validity.

Key gap filled, not explicit in the docs: nothing previously called ollama_client.run_cycle() on a schedule or connected its output to render_resolver.py or the WebSocket send. Added run_render_loop() in connection.py, ticking every GLOSS_CYCLE_INTERVAL_MS (new config constant, 1500ms, matching the System Architecture text's own "~1.5-2s" cadence description). Also added the current-mode state (module-level, default "video") since nothing else tracks which render mode is active.

Correctness fix made while wiring this together: whisper_service.run_loop() and the new render loop both call into blocking synchronous code (GPU transcription, an HTTP round-trip to Ollama) directly from an asyncio loop, which would stall audio ingestion and chunking during every call - contradicting the architecture's own "chunk N+1 recording continues while chunk N is being transcribed" pipelining intent. Fixed by wrapping both calls in asyncio.to_thread().

Bug found and fixed during testing: connection.py's receive loop used websocket.receive() to distinguish binary/text messages, but a client disconnect arrives through that low-level method as a plain {"type": "websocket.disconnect"} message, not as a raised WebSocketDisconnect exception (that only happens with the higher-level receive_bytes()/receive_text() helpers). The disconnect handler was never firing. Fixed by checking the message type explicitly and raising WebSocketDisconnect.
