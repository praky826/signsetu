# Phase 10 Completion Summary — Frontend Shell & Avatar Idle State (Step 2)

Files created: frontend/index.html (import map resolving "three" and "three/examples/jsm/" to a pinned CDN build, required since avatar.js and SignEngine.js use bare ES module specifiers - main.js loaded as a module; Start Capture button; Video/Avatar mode toggle defaulting to Video; status indicator placeholder; output window div containing an avatar-container div and a video element); frontend/style.css (fixed-position ~300x200px output window bottom-right, display toggle classes for the two render elements); frontend/main.js (calls avatar.js's initAvatarScene(container) once, constructs one SignEngine instance from the resolved model, leaves hooks for later phases unimplemented).

Real bug found and fixed, in our own code only, no reused file edited: the actual human.glb's bones are all named with a trailing numeric suffix (e.g. "mixamorigRightArm_033"). SignEngine.js's internal bone matcher only checks whether a normalized name ends with an expected pattern, which the suffix breaks - confirmed via direct browser testing that only 1 of 66 bones mapped. Fixed in main.js by stripping trailing "_<digits>" suffixes from bone names after the model loads and before constructing SignEngine; verified this restores all 54 needed bone mappings.

Second real bug found and fixed: after the bone-name fix, the avatar still rendered as a fully invisible/uniform-color canvas with Three.js r0.128.0 (the version SignSetu.docx suggests as an example, originally chosen to keep avatar.js's renderer.outputEncoding = THREE.sRGBEncoding working). This was confirmed as a genuine rendering bug, not a testing artifact, since it reproduced identically in the developer's own real Chrome browser. Extensive isolation (CPU-side skinning math checked correct; fresh MeshStandardMaterial instances rendered fine; the loaded materials' own properties looked normal; WebGL float vertex textures confirmed supported) narrowed it to Three.js r0.128.0's GPU skinning path itself failing specifically for this model's skeleton, reproducible by setting skinning=true on any material regardless of source. Fixed by re-pinning to Three.js r0.160.0 in index.html's import map; verified the exact same rig and materials render a fully visible, correctly colored avatar with no console errors, and the SignEngine self-test animation (hip tilt, arm raise, forearm bend, fist, reset) completes correctly. The sRGBEncoding property is silently ignored under r0.160.0 (a no-op property set, not an error) and produced no visible color regression on inspection.

Human step: none remaining for this phase. The visual checkpoint the phase document calls for was completed jointly - the developer's own Chrome screenshot confirmed the bug was real, and the subsequent fix was verified as working correctly directly in the browser tool.
