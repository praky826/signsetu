Bugs found in the reconnect path (Fallback C), not caught by earlier phases since each was tested in isolation with only a single connect, never a reconnect-then-inspect pass:

1. Double WebSocket connect on every reconnect: sessionManager.js's reconnect() called wsClient.js's reconnect() itself, then also invoked its onNewStream callback, which is main.js's validateStream -> handleValidStream chain that calls connect() again once real audio is confirmed. The first socket was never closed, leaking one open backend connection (and one abandoned server-side task) per reconnect. Fixed two ways: wsClient.js's connect() now closes any existing socket before opening a new one (so it is safe to call from any path), and sessionManager.js's reconnect() no longer connects at all - it only re-attaches the stream-end listener and lets the existing validate-then-connect chain handle it, matching the original single-connect design.

2. Two AudioContext leaks on reconnect: streamValidation.js's sampleSignal() and audioGraph.js's startAudioGraph() both construct a fresh AudioContext on every call, including on reconnect, without closing the previous one. Fixed by tracking the previous AudioContext/graph in each module and closing it (via a new sharedAudioContext close in streamValidation.js, and by calling the existing stopAudioGraph() at the top of startAudioGraph()) before building the new one.

No other cross-boundary function signatures changed. Data structure shapes (stable_words/provisional_context/allowed_vocab, word/hamnosys/videoPath, word/renderType/assetRef/sessionId) are unchanged and consistent everywhere they are produced or consumed.
