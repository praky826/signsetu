# Phase 14 Completion Summary — Status Indicator & Degrade Handling (Fallback B, frontend half of Fallback G)

File created: frontend/status/statusIndicator.js (Status enum with the five frozen values, setStatus(), getStatus(), setProcessingDelay()). Files extended: tabCapture.js now calls setStatus(LISTENING) on successful capture; streamValidation.js calls setStatus(NO_AUDIO) on the no-audio-tracks branch and no longer writes a non-enum "waiting for playback" placeholder text (LISTENING already covers "capture active, waiting for/processing audio" per Fallback B's own definition, so no separate state was needed); wsClient.js calls setStatus(RECONNECTING) on socket close and dispatches latency_status control messages to setProcessingDelay(). Backend file extended: backend/ws/connection.py's run_render_loop() now tracks latency_tracker.should_degrade() and sends a new control message, {"type": "latency_status", "degraded": bool}, only when the value actually changes, never every cycle.

Cross-boundary addition: the backend-to-frontend message shape above, plus a discrimination rule (Phase 14 decision, not specified in the docs): incoming WebSocket text messages are treated as a control message if they have a "type" field, otherwise as a render instruction, since the frozen render-instruction shape has no "type" key of its own.

No ambiguities beyond the "waiting for playback" correction above, which was a self-inconsistency from Phase 11's own placeholder rather than a document conflict.

Verified with real execution: IDLE is the correct initial state; a real video-only (no audio track) MediaStream correctly triggers NO_AUDIO with the message banner shown; a real oscillator-fed audio stream correctly stays at LISTENING through capture, validation, and WebSocket connect, with no spurious intermediate state; actually closing the live WebSocket correctly triggers RECONNECTING; setProcessingDelay() correctly toggles PROCESSING_DELAY and reverts to LISTENING on recovery. No human step is required for this phase.

Verified end to end with a simulated high-latency chunk: should_degrade() correctly flipped to true and average_latency() reflected it accurately, and a full live-server round trip (real Ollama, real render resolution, real WebSocket) confirmed no regressions.
