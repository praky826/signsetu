# Phase 15 Completion Summary — Seek/Pause Monitoring, Reconnect & Debounce (Step 18 frontend half, Fallback C/H)

File created: frontend/session/sessionManager.js (initSession(), getSessionId(), startSeekMonitoring()/stopSeekMonitoring(), attachStreamEndListener(), reconnect()). Files extended: main.js now calls initSession() once on the very first successful capture only, attaches the stream-end listener on every capture/reconnect, and starts seek monitoring once validation succeeds; wsClient.js and renderQueue.js now import sessionId from sessionManager.js instead of wsClient.js's own Phase 12 placeholder generator, completing the sessionId-ownership handoff the frozen convention always specified. Added a Reconnect button to index.html/style.css (Fallback C's "one-click Reconnect" needs a visible UI element, not listed in this phase's own file list but required, same situation as Phase 11's retry button).

Cross-boundary addition: none new - reuses the {"type": "seek", "sessionId": "<id>"} control message already decided in Phase 9.

Key decisions, not specified in the docs: sessionId increments by exactly 1 on each confirmed seek (wrapping within uint32), matching "monotonically-incrementing" literally, rather than generating a new random ID. A frontend-only SEEK_DEBOUNCE_MS (175ms) was added to sessionManager.js, mirroring backend/config.py's same-named constant's value, since that Python constant cannot be imported into JS (flagged in the Phase 14 consistency check, resolved here). A genuinely new stream is never distinguished from a mere reconnect to the same content: a MediaStream object reference cannot reliably tell them apart, so every reconnect keeps the existing sessionId, relying on session_state.resume_session() already treating an unchanged sessionId as "unfreeze, keep buffers."

Ambiguity encountered and resolved: Step 18 requires seek detection via AnalyserNode signal discontinuity, with no exact algorithm given. Initially implemented as a silence-then-resume pattern within a 150-1500ms window - see the critical bug below, which changed this significantly.

Critical bug found via your real-world test, not caught by this session's own synthetic testing: with real narrated YouTube speech playing, the backend log showed the session incrementing on almost every single audio cycle. The 150-1500ms detection window was catching ordinary pauses between words and sentences in real speech - completely normal narration cadence, not seeks - and every false trigger wiped the chunker and rolling text buffer, which is exactly why no signs ever appeared: nothing ever survived long enough to reach a real gloss cycle. This session's own verification had only used clean, isolated silence gaps, which never exposed how aggressively real, continuous speech would trigger it. Fixed by raising the thresholds substantially (4000-10000ms) so ordinary speech, including deliberate narration pauses, essentially never triggers a false seek - accepting that some genuine seeks will now go undetected, since that failure mode is far less costly than destroying good progress on every breath. Re-verified directly afterward: six simulated realistic speech pauses (300ms-1800ms each) produced zero false increments, while a genuine 5-second gap still correctly triggered exactly one.

Also verified: sessionId is created once and stays stable through validation and WebSocket connect; a single genuine seek correctly produces exactly one debounced increment and one seek control message; Fallback C's reconnect flow (verified by directly invoking the attached handler, since a synthetic test track does not naturally fire a real 'ended' event) correctly shows RECONNECTING and the button, and clicking it correctly re-triggers the real capture flow.

Addendum, found via a second real-world test after the fix above: with the false-seek bug fixed, real story content flowed through the full pipeline for the first time (real transcribed sentences, real gloss cycles). This surfaced a second, unrelated critical bug that had existed since Phases 3, 7, and 9: render_resolver.py and cislr_index.py were sending assetRef as a raw Windows filesystem path (e.g. "C:\signsetu\assets\placeholder\unknown_word.png"), and assets/ was never mounted as a static route on the backend at all. Chrome correctly refuses to load file:// resources from an http://-served page, so every single unresolved word (which was every word, since no CISLR clips are cached yet) silently failed to load its placeholder image - this, not GPU contention, was the actual cause of the black output window and collapsing frame rate you saw, confirmed by the browser console showing 44 identical "not allowed to load local resource" errors. Fixed by mounting assets/ at /assets in main.py and changing both files to produce URL paths instead of filesystem paths. Verified end to end with a live in-process test: a real render instruction's assetRef is now a URL, and fetching that URL from the running server returns 200.
